# 版本与发布

日常功能改动先提交并通过 CI，不为每次改动创建 Release。准备好一组可用功能、完成安装包和升级验证后再发布正式版本。

正式标题统一使用 `v主版本.次版本.修订号 - 功能主题`，例如 `v0.7.0 - 照片裁剪与经历编辑`。标题不使用表情、宣传语或临时任务名称。功能版本递增次版本，兼容性修复递增修订号。

开发版本采用 `0.7.0-dev.1` 一类的版本号，下载包名称也包含开发标记。发布说明保留具体变更、升级方法和实际验证结果。正式 tag 对应通过 CI 的提交，公开下载文件应核对 SHA-256。

草稿组装输入准确候选提交、六项成功 CI 的 run ID、版本、功能主题和说明；标题自动采用 `v版本 - 主题`，测试数量读取对应 CI 的实际报告，不沿用旧版本数据。重复组装只可更新同一候选的草稿，公开版本不被覆盖。

项目通过 GitHub 分发源码和本地运行包。开发包先通过 CI、安装与实际 PDF 验证，再按上述规则集中发布。

升级基线统一记录在 `scripts/upgrade-baseline.json`，包含正式 Windows 下载包的版本、名称和 SHA-256；本地重新构建的同版本文件不能替代已发布包。下载到 `tmp/upgrade-baselines/v版本/` 后运行 `npm run test:upgrade`，检查原文件、三份简历、回收站、技能与补充信息表单、单份与整库恢复、旧程序重新打开和新版重启。

发布组装核对升级报告对应的候选 ZIP 摘要，采用实际文件数量；macOS Intel 与 Apple Silicon `.app` 同时要求构建、启动和离线 PDF 报告，核对 ZIP 内版本、运行组件摘要与可执行权限，再收录到草稿。早期版本的实际验收记录见 [v0.9.0 发布准备](release-0.9-readiness.md)。

Windows 候选还运行 `npm run test:journey`，串联首次启动、填写与图片、PDF 下载、保存冲突、重启草稿恢复、单份及整库备份恢复。报告在 `tmp/packages/user-journey-smoke.json`，PDF 和步骤截图在 `tmp/pdfs/user-journey/`；发布前需逐页渲染复核。发布组装还核对报告版本、候选 ZIP 摘要和全部流程结果，将用户流程记录写入 `release-validation.json`。正式发布文件与验收依据见 [v0.11.0 发布验收记录](release-0.11-readiness.md)和 [v0.11.1 发布验收记录](release-0.11.1-readiness.md)。
